# CLAUDE_WORKFLOW（Claudeの共通作業プロトコル）

基本の流れ: 目的を受け取る → 必要な調査 → 実装 → テスト → dry-run → 結果確認 → 状態更新 → commit
ユーザーの判断が必要な場面（仕様変更・本番影響・外部公開）では、勝手に進めない。
現在地は `docs/PROJECT_STATUS.md` を参照（このファイルは手順だけを定める）。

## 1. 作業開始時
- 最初に確認するのは次の3つだけ: `docs/PROJECT_STATUS.md` / `git status` / 必要なら直近の `git log`
- その後は、今回の目的に必要なファイルだけを調査する。プロジェクト全体を毎回読み直さない。

## 2. 調査
- 集計（Python）・ファイル検索・ログ確認・設定確認・既存コードの追跡・dry-run・テストは、Claude自身が実行する。
- ユーザーにコードや大量のログの貼り付けを求めない。

## 3. 実装
仕様が明確なら、途中で細かい確認を挟まずに進める。次の場合だけは作業を止め、確認事項を最小限にまとめて質問する。
- 既存仕様を大きく変更する
- 新しい外部サービスを導入する
- 本番データを大量に変更する
- 不可逆な操作をする
- ユーザーの目的や優先順位が複数に分かれる
- 既存機能とのトレードオフが大きい

## 4. 変更方針
- 最小限の変更を優先する。動いている機能を不要にリファクタリングしない
- 既存のインターフェースをできるだけ維持する。同じ処理を重複して実装しない
- 新しい依存関係は、必要性を確認してから入れる
- 既存の設定・環境変数・GitHub Actions を不用意に変更しない

## 5. 検証（コード変更後にまとめて実行する）
1. 構文チェック（`.venv/bin/python -m py_compile ...`）
2. 既存テスト（現状 `tests/` は無い。無い場合は既存の dry-run など、実行できる検証方法を使う）
3. 必要な範囲の単体的な確認（境界値・異常系・変更前後の比較）
4. dry-run（Discordへの送信なし・state更新なし）
5. 実行結果の確認

結果は、数値と成否だけを簡潔にまとめる。

## 6. commit
安全なコード変更で、検証が成功した場合は commit まで自動で進めてよい。commit の前に次を確認する。
- 変更ファイルが意図したものだけであること（`git status` / `git diff --stat`）
- 検証が成功していること

## 7. push・本番反映
次の操作は、ユーザーの明示的な許可がある場合だけ実行する。
- `git push`
- GitHub Actions の本番実行（`gh workflow run` を含む）
- 本番データの変更
- Discord などへの実データ配信を伴う変更
- 外部サービスの変更

最初の指示で「pushまで」「本番反映まで」と明示された場合は、その範囲で実行する。
`PROJECT_STATUS.md` の「本番反映時の検証手順」にある push と Actions 実行も、この条件に従う。
push の前には `git pull --rebase origin main` を実行する（bot が state を頻繁に commit するため）。

## 8. PROJECT_STATUS.md の更新
作業終了時、次のどれかが変わった場合だけ更新する。不要な文章は書き足さない。
- 本番機能
- 重要な設定
- 重要な commit
- 新しい問題
- 問題の解決
- 未着手事項
- 運用方法

## 9. ユーザーへの最終報告
長い作業ログや大量のコードは出さない。原則として報告するのは次の項目だけ。
- 何を変更したか
- 検証結果
- dry-run 結果
- commit ID
- push・本番反映の有無
- 問題点
- ユーザーの判断が必要な事項

## 10. トークン節約
- 同じファイルを何度も全文読まない。必要な範囲だけ読む
- 大量のデータは Python などで処理し、結果だけを確認する
- 大量のコードを会話に出力しない。調査結果は短く要約する
- `PROJECT_STATUS.md` に記録済みの情報を再調査しない
- 不要な確認質問をしない

## 権限の早見表
| 自動で進めてよい | 原則として確認する |
|---|---|
| 調査・ファイル検索・Pythonでの集計 | push・本番反映 |
| テスト・dry-run | 外部サービスの変更 |
| 小規模で安全なコード修正 | 破壊的な操作 |
| ドキュメント更新 | 大規模なリファクタリング |
| commit（検証成功が前提） | 仕様そのものを変える判断 |
